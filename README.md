# AI-Lore

A methodology for building a **Payload** — software, a campaign, a specification, anything that benefits from persistent context — with an AI partner that remembers across sessions, challenges its own prior decisions, and stays in character while it works.

The Payload is what you produce. Everything else exists to serve it: a Memory model that compounds across sessions — status, focus, journal, blueprint, knowledge tree, action tree — and a stance system that shapes how the AI thinks, writes, and pushes back. Session 10 starts with everything sessions 1 through 9 learned. The compound curve is the point — but compounding alone is not enough if the AI shows up as a different collaborator every time. AI-Lore is built so it does not.

---

## The shape

AI-Lore organises every project around six terms. Learn them once and the rest of the methodology reads cleanly.

| Term         | What it is                                                                                  |
| ------------ | ------------------------------------------------------------------------------------------- |
| **Project**  | The root directory where work happens.                                                       |
| **Payload**  | What the Project produces. Project root minus the Lore folder.                               |
| **Lore**     | The support system. Lives at `<project>/.ai-lore-<project_name>/`.                           |
| **Memory**   | The Project's record of its own thinking — status, focus, journal, blueprint, trees.         |
| **Upstream** | Pristine, pinned AI-Lore checkout. Versioned — old and new pins coexist during migration.    |
| **Process**  | The built, substituted documents the AI actually reads. Single-version, regenerated by build. |

Upstream is source. Process is dist. Sessions only ever read Process; Upstream exists so Migrator can hold two versions side by side during an upgrade.

## How a session runs

You open an AI in your project root and say: *read `ai_readme.md`*. That is the four-word handshake. Everything else flows from there.

1. **Universal load.** `ai_readme.md` walks the AI through six pillars — project structure, stances, modes, operating rules, the tracker, the memory model — in fixed order. The AI is now AI-Lore-shaped for the rest of its lifetime.
2. **Orient.** It reads `memory/status/status.index.md`, walks the tracker chain into the active focus, and picks up the last session's handover. Three-second orientation is the test.
3. **Pick a stance.** The Human Lead names one. The AI loads that stance file and applies its dial profile from cold.
4. **Work.** The session produces against the focus's gate, in the mode the work demands, recording everything as it goes.
5. **Close.** The session writes a journal entry, updates status, and hands the work over to whoever opens the next session.

No setup ceremony. No re-explaining the Payload. No manually loading files.

## The four dials

A **stance** is the identity a session operates as. It is a four-dial configuration applied across two domains — **Chat** (how the AI talks) and **Work** (how the AI writes).

| Dial          | Settings                                       | What it controls                                     |
| ------------- | ---------------------------------------------- | ---------------------------------------------------- |
| **Voice**     | Contractor / Tech Lead / CxO                   | How the AI communicates and writes                   |
| **Precision** | Goal-oriented / Fine-tuned / OCD               | How deeply it reads and how much detail it captures  |
| **Pushback**  | Supportive / Constructive / Critical           | How hard it challenges — you, prior artefacts, itself |
| **Ownership** | External / Employee / Partner                  | How invested it is in the outcome                    |

A stance picks one setting per dial. **Architect** is CxO / Goal-oriented / Critical / Partner — the design collaborator who challenges, stays, and co-owns. **Strategist** is CxO / Goal-oriented / Critical / External — the clinical evaluator who challenges, delivers a verdict, exits. Same Voice, same Pushback, very different shape — driven entirely by the Ownership dial.

**The dials do not suspend.** Not when the AI shifts from chat to producing, not when it presents findings, not when the work gets long. A wall-of-text delivery is not a formatting problem — it is a dial collapse, and the methodology names it as such. The Human Lead can invoke `redial` and the session re-applies its dials from cold.

Two stances are protected infrastructure, present in every project: **Auditor** (evaluates whether Memory is shaped to the pillars) and **Migrator** (handles version migration and first-run bootstrap). Plugins ship the rest by composing pre-built example profiles — Architect, Editor, Strategist — under whatever names and dial settings their domain needs.

## Modes

Stances describe *how* the AI behaves. **Modes** describe *where the work is happening* and how much to trust the Memory it finds. Every session is in one of four, always.

- **Reflecting.** The understanding the work needs is not yet in Memory. Build the focus, build the knowledge nodes, then move on.
- **Planning.** The approach is understood; decompose it into phases the next mode can execute.
- **Executing.** The plan is in place. Produce Payload against the gates.
- **Salvaging.** The Memory accumulated around the current approach can no longer be carried forward. Rewrite, then re-enter one of the other three.

Stances are mode-insensitive — your dials do not change when the work shifts from Reflecting to Executing. What changes is what gets touched.

## Memory

Memory is what makes session 10 cheaper than session 1. Five components:

| Component         | Role                                                                  | Required |
| ----------------- | --------------------------------------------------------------------- | -------- |
| **Status**        | Three-second orientation. Where the project is right now.              | Yes      |
| **Journal**       | Continuity wire. One file per session, append-forward, never edited.   | Yes      |
| **Blueprint**     | Production rules and standing contracts the Payload must honour.       | Yes      |
| **Action tree**   | Decomposition for focuses too large for one tracker.                   | Optional |
| **Knowledge tree**| Curated, durable insights that compound over time.                     | Optional |

**Status, focus, and action-tree nodes are all instances of one primitive — the tracker.** Every tracker carries the same four fields: a stack of children, an active child pointer, a journal trail, and a gate. The tracker chain runs from `status.index.md` down through the active focus into whatever decomposition the work needs. Each node adds exactly one thing the parent does not already say.

**Blueprint is distinct from the knowledge tree.** The KT carries what the project has *learned*. The Blueprint carries what the project has *committed to*. Learning compounds; rules govern.

Across all five components, **emptiness is a valid state.** A blueprint with placeholder sections, an absent action tree, an empty knowledge tree — none of these are gaps. They mean the project has not yet committed to anything in that area. Memory grows organically as commitments accumulate.

## Verbs

A **verb** is a named operation the Human Lead invokes by saying its name. Verbs are how you reach into a running session and ask for a specific operation without having to explain what you want.

| Verb         | What it does                                                                                |
| ------------ | ------------------------------------------------------------------------------------------- |
| **Reshape**  | Content is right, shape is wrong. Move it around in place.                                  |
| **Rewrite**  | Content cannot be carried forward. Return to sources, produce a fresh replacement.          |
| **Digest**   | Read the target with Critical pushback. Report gaps, contradictions, stale references.     |
| **Split**    | A wall-of-text delivery becomes ranked findings, one at a time, in voice.                   |
| **Redial**   | The session has drifted off its dials. Re-apply them from cold, name the drift it is leaving. |
| **Dictation**| Feed the session raw text and have it polished against the target artefact's voice first.   |

Redial is the first verb added from observation rather than design. It exists because the same correction kept happening across sessions; naming it turned a recurring failure into a loadable word. Its existence is evidence the universal-load architecture works — the methodology can grow new operations without rewriting itself.

## Plugins

Every project declares a **plugin** in `workspace.yaml`. The plugin is your domain-specific layer: it ships a stance catalogue, a blueprint seed, and any conventions that apply only to your kind of work.

| Plugin    | Domain                       | Example stances                |
| --------- | ---------------------------- | ------------------------------ |
| **sdlc**  | Software development          | Architect, Tech Lead, Auditor  |
| **spec**  | Methodology / process design  | Editor, Strategist             |
| **ttrpg** | Tabletop RPG campaigns        | Game Master                    |

The protected infrastructure stances — Auditor and Migrator — are present in every project regardless of plugin. The build fails on any attempt to redefine them.

Plugins are a build-time concept. The composed Process is plugin-blind: the AI loads from plugin-agnostic paths under `<lore>/process/` and never knows which plugin produced what it is reading.

## Why this works

Three insights about long-running work with LLMs.

### Planning is cheap; discipline is the lock

LLMs can read an entire project, hold it in context, and produce a detailed plan in minutes. AI-Lore locks in the *discipline* of planning, not the plan itself. You plan before every stage. You execute. Execution reveals new information. You replan. The cycle is tight — hours, not months. The plans are disposable. The discipline of producing them is not.

### Knowledge compounds

The hardest problem with AI-assisted work is not output quality — it is the inability to remember anything. Every new session starts from zero.

AI-Lore fixes this with a memory model where session N loads exactly what it needs from sessions 1 through N–1, in a fraction of the tokens it would take to rediscover. The compound curve is real but back-loaded. For a two-session task it barely pays for itself. For a multi-month effort it is dramatic. And it only works if you review what the AI writes — the AI populates the memory; your review makes it trustworthy.

### The AI is a collaborator with a posture

Most AI workflows treat the model as an output machine: prompt in, artefact out, repeat. AI-Lore treats it as a collaborator whose posture you can dial in. A skeptical co-owner who challenges your prior plan. A clinical evaluator who delivers a verdict and exits. A pragmatic implementer who stays in scope. Same model, different stances, summoned on demand.

The dials persist through delivery. A Critical stance challenges its own prior output, not just yours. A Partner stance co-owns the outcome instead of delivering and disappearing. A CxO voice stays lean in the artefact, not just in chat. The stance you shape with is the stance you write with — that persistence is what makes the partnership real instead of cosmetic.

## Who this is for

Experienced practitioners — people who know their domain well enough to evaluate AI output critically and make sound decisions without guidance. The process does not teach you your craft. It gives you a structure for practicing your craft *with AI* that does not degrade over time.

**Use it for the right work.** Not everything needs this. A quick task, a one-off question — just do it. AI-Lore earns its keep when the work has dependencies, spans sessions, or makes decisions that constrain future work. The test: would you benefit from the AI remembering what happened last session? If yes, use it. If not, skip it.

> **Fair warning.** This methodology is deliberately demanding. It will ask more of you than unstructured AI work, not less. The payoff is back-loaded: early sessions feel expensive, by session ten the compounded memory means the AI is productive immediately. The first few sessions pay for the next fifty — but only if you do the work. Rubber-stamping the artefacts gives you all the overhead with none of the returns.

## Getting started

1. **Bootstrap.** Run the bootstrap flow — see [bootstrap/README.md](./bootstrap/README.md). It clones the upstream pin, runs the build, creates the Lore folder, seeds Memory from the skeleton, and installs `ai_readme.md` at the Project root.
2. **Open a session.** *Read `ai_readme.md`*. That is the prompt.
3. **Name a stance.** The session lists what the plugin ships. Pick one.
4. **Work.**

Already on an older version? Migrator drives the upgrade — pin flip, rebuild, then an interactive Memory reshape against the version-specific playbook. The old pin stays on disk until you confirm the new one is proven; rollback is one pin flip and a rebuild.
